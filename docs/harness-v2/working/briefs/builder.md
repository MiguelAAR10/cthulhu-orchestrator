## What the Owner asked for
A harness that is fast, concurrent, idempotent and reliable; configurable instead of rigid (which model each role uses, herdr or Orca as the terminal driver); aware of the machine (RAM, CPU, disk) when deciding how many agents to run; with real agent-to-agent communication and memory; where code and git are the source of truth; that does not drift from the product value of the story; and that closes every loop it opens. Proposals P1 to P8 in the plan are approved.

## Activities (default order)
C1 **Configuration, not constants.** New package `internal/config`: user file (~/.config/orq/config.json, ORQ_CONFIG for tests) merged with project file (<root>/.orq/config.json). It decides: terminal driver (herdr|orca); per role (atena, orquestador, planificador, astra, verificador, scout) the agent kind, model and effort; per worker difficulty (baja|media|alta) and agent kind the model and effort; resource rules (C3). Defaults equal today's behaviour. Remove the hard-coded tables (`porRol`, `plan.Modelo`, model names in code and guides print from config). `orq config ver` prints the effective configuration and where each value came from; an unknown field is an error.
C2 **Terminal driver port.** An interface for what orq needs from a multiplexer (create tab/pane, start an agent with args and env, deliver a nudge, read status, close) with the herdr adapter moved behind it and an Orca adapter built on the `orca` CLI (run `orca agent-context` for its machine-readable command schema; the launch regex in internal/gate lists the Orca commands orq already recognises). Every call has a timeout and an idempotency story: a timed-out start is "unknown", checked before any retry, never a blind second launch. Tests use a fake driver; live herdr tests stay opt-in as today.
C3 **Machine awareness.** `sysinfo` reads MemAvailable, CPU count and load from /proc. Launch capacity = min(configured max, what RAM and CPU allow with a configurable per-agent budget and reserve); the gate and `slice lanzar` deny a launch that does not fit and say why; `orq status` shows RAM, CPU, disk and the capacity it derives.
B5 **Isolation.** Per the decisions in the plan and Astra's cut: independent clones without shared or hard-linked objects; work returns as a git bundle that orq verifies and fetches; orq never runs git with its cwd in a worker repo; the exam, `--sano` and the integration re-run always execute inside `internal/sandbox`; protected paths are enforced on the ingested diff; closing never trusts a state that claims CERRANDO or an `integrado` SHA without re-checking against the trusted contract; slices opened by orq 1.0.0 are converted with their old processes stopped and re-verified; `.orq` is absent or read-only inside every box. Exit test: validacion/aislamiento.sh passes including its part 2 (no `--todo` needed). `internal/sandbox` and that script are being finished by another worker on harness-v2; the orchestrator will tell you when to `git merge harness-v2`. Do C1-C3 first.
B6 **Launch inside the box.** Workers start through a PATH shim that execs the agent inside the sandbox (the spike proved this is the route herdr accepts). Agent config dir: no credential is created or copied by you. Implement and test with a simulated agent binary; real launch needs a dedicated credential from the Owner, so when none is configured `slice lanzar` refuses with a message naming the config key. Dependencies follow P5 (read-only bind by default; private copy plus offline frozen install when the task changes them). Skills follow P6 (per-role allowlist, read-only, without skills that own worktrees, merges or PRs).
C6 **Channel (P1).** Sender identity comes from the launcher's box environment, not from `--de` (ignored inside a box). Pull inbox per role is the source of truth; the pane receives only a one-line doorbell. `cierre` and `estado` carry structured data that the harness reads. Idempotency key derived when absent. A message to a closed attempt is rejected for every type. Keep the on-disk model close to A2A's task/message/artifact so a gateway can be added later; no HTTP.
C4 **Measure value (P2).** Per slice, lane and role: wall time, attempts, verifications, sessions opened, and tokens when the agent's transcript exposes them (best effort, labelled as such). `orq metricas` reports it per lane.
C5 **Lean by default (P3, P4, P7).** One worker unless zones are declared disjoint with a reason; Astra and scouts only for large or risky slices; a decisions file per slice that every worker and verifier contract points to. Skills and guides updated to match (use the writing-for-agents skill for those files).
A4 **CI and honest docs.** GitHub Actions workflow running gofmt check, vet, `go test -race ./...`, staticcheck if available without adding a module dependency, and the scripts in validacion/. README and docs/REGLAS-HARNESS.md say only what the program enforces, including what a worker can still do.
