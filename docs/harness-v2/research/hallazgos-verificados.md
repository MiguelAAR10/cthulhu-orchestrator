## 2. PARTIAL findings: what the code actually does (questions for the authors)

**H15 (AA).** The partial `watch` reading only affects the scratch quota. The gate measures free disk live on every launch (gate/gate.go:136-143) and denies if it cannot measure. So "disco lleno" cannot slip through this path; only an under-counted scratch total can. The fixed temp name is real, but the last rename wins and the data stays valid JSON. Question: did you have a full-disk case in mind that gets past the gate's live check?

**H18 (AA, FA).** A name collision mostly blocks rather than hijacks. If a same-named agent is alive and this project's diario has no `panel` event for it, `abrirSesion` refuses: "ya existe un agente … que orq no lanzó" (app/sesiones.go:69-72). Hijack is possible only if this project once launched that name, the agent died, and another repo now has one with the same name. In that case the launch adopts it and sends the contract to the other repo's agent. Question: is P6 in pilot-log a case of this, or of counting workers in the gate?

**FA "at the limit it rejects; rejecting is losing the work" (part of H16).** Nothing is lost. The capacity check runs before the plan or team is touched (app/workers.go:124-133), so the task stays `pendiente`. What is missing is someone to retry.

**FA/AA "the ID comes from counting lines, so it can repeat" (part of H19).** The ID is the number of parsed messages + 1, not the number of lines (canal.go:104, 153-160). Delivery events do not count. A repeat needs a lost message line (a torn line) or the file being deleted (H2). The second case happens on every slice close, which is the bigger cause.

**H20 HALT without rename (FA).** It is harmless. `ReadHalt` only checks that the file exists (state/state.go:59-64), so even a torn HALT still halts.

## 3. Important findings none of the reports mention

1. **`orq sesion cerrar` saves a session map that can be minutes old.** It loads `sesiones.json` (cli/sesion.go:28), then `CerrarWorker` may run a full verification (minutes), then `CerrarSesiones` writes that old map back (:87). Any worker launched or closed during the verification is overwritten. This widens H3/H4 from milliseconds to minutes.
2. **One bad line in memory hides all of it.** `memoria.Load` fails the whole file on one unreadable line (memoria/memoria.go:115-117), unlike the diario and the channel, which skip bad lines. `MemVigente` and `cli/v03.go:536` drop that error, so a single torn line removes all memory from every new session with no warning.
3. **Deleting the channel on close breaks memory evidence.** m13 cites "canal c16". After a close, the channel restarts at c1, so a later "c16" is a different message. Evidence by message ID cannot be trusted across slices (H2 + H26).
4. **Atena can approve its own card** (H31 detail). The guard assumes the Owner's terminal has no ORQ_ROL, but Atena runs in that same pane. This breaks the v2.0 rule that the Owner decides each story.
5. **The close error points to a dead end** (H12 detail). After refs are lost, `confiable` says "close it as rejected" (contrato.go:116). But rejection refuses CERRANDO and INTEGRANDO (cierre.go:173-175), so the slice cannot be closed either way without editing files by hand.
6. **`MarcarEntregado` appends to the channel without the flock** that `Append` holds (canal/canal.go:111-120 vs 88). It is usually safe on local ext4 because O_APPEND writes are small, but it is the only unlocked writer of that file.
